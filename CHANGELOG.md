# Changelog

All notable changes to `ranetrace-php` will be documented in this file.

This file starts here, so releases before it are not recorded; the git history is the record for those.

## [Unreleased]

### Changed
- **The contract describes an invalid item as refused on its own.** The backend now validates each item of a batch by itself: an invalid one is not stored and is counted as failed in a 200, and the rest of the batch is stored, where before one invalid item failed the whole batch with a 422. `contract/responses.json`, the item and envelope notes, and the docblocks that gave the old rule as the reason for a guard now say so; a 422 is described as a request body of the wrong shape. The SDK's behaviour is unchanged: a failed item was already final, and a 422 is still dropped with a feature pause. The guards stay, because an item they let through malformed is still lost. The contract also notes that an error's, a log record's or a breadcrumb's `message` may be an empty string. Nothing to do on upgrade
- The worker's log line for a 422 now says the request body was rejected as malformed, which indicates a client bug, instead of blaming schema drift or malformed items: an invalid item no longer causes a 422. No behaviour changes, and nothing to do on upgrade

## [1.0.9] - 2026-10-05

### Changed
- **Breaking: the buffer no longer expires, and `batch.buffer_ttl` is gone.** `FileBuffer` discarded a whole type's spool once its file had gone `batch.buffer_ttl` seconds (3600 by default) without a write, with only an info line in the internal log. So a quiet host whose cron had stopped lost everything it had captured, and the stalled drain that `oldestTimestamp()` exists to reveal disappeared with it. The API stores each item's own time and accepts an old one, so a backlog is still worth delivering. A spool is now kept until it is delivered, and `batch.max_buffer_size` is its only bound: past it the oldest items are dropped, with a logged overflow. On upgrade, remove `RANETRACE_BATCH_BUFFER_TTL` from the environment and `batch.buffer_ttl` from an array config if you set either; both are ignored now
- **Breaking for a custom buffer: `Buffer\BufferInterface` requires `returnItems(string $type, array $envelopes): void`.** The worker puts every undelivered envelope back through it rather than through `addItems()`. It takes envelopes as `take()` handed them out, puts them back at the head in the order given and unchanged, keeps the newest items when that overflows `batch.max_buffer_size`, and logs a failure itself, because the caller has nowhere else to keep the items. A host that wrote its own buffer has to implement it; there is no default. A host on `FileBuffer` has nothing to do
- **Breaking: `Http\BatchOutcome::unprocessedPayloads()` is replaced by `unprocessedItems()`.** It returns the whole items the server named in `unprocessed_indexes`, not just their payloads, each once and in batch order, whatever order the server named them in; an index outside the batch names nothing. It is generic over the item shape, so `ranetrace/ranetrace-laravel` can hand it its own envelopes. A caller of the old method switches to the new one and reads `['data']` from each item if it wants the payloads

### Fixed
- **A batch that could not be delivered keeps its ids and capture times, and goes back to the front of the buffer.** The worker put a failed batch, the items the server reported as unprocessed and the items deferred to keep a request under the byte budget back through `addItems()`, which gave each a new id and the current time and appended it. So a batch failing for hours looked freshly captured to `FileBuffer::oldestTimestamp()`, which is how a stalled drain is told apart from one waiting for its next run, and it was sent after everything captured since. They now go back at the head of the buffer, unchanged, and a failed batch lands ahead of the items deferred from it, where it was before. Nothing to do on upgrade
- **Items the worker cannot put back are logged as lost.** When putting a batch back failed, because the buffer lock stayed contended for `batch.lock_wait`, the buffer directory was not writable or the write failed, the items were gone and only a generic lock warning said so, which read like a capture that had been skipped. Each such loss now writes `Could not return items to the buffer, items lost` to the internal log at error level, with the type and the number of items

## [1.0.8] - 2026-10-05

### Fixed
- **A float JSON cannot spell no longer costs the item it is in.** `json_encode` refuses the whole value when one float in it is INF, -INF or NAN, as a ratio divided by zero in a log context or an event property is. The file buffer then failed to write, so the item was dropped with an internal log line, and in a host whose buffer does not encode, the batch carrying it could not be sent at all. Such a float in a log record's context or extra, an event's properties, a throwable's `context()` or a JavaScript error's context or breadcrumb data is now sent as the string `"INF"`, `"-INF"` or `"NAN"`, through `Support\DataSanitizer`. A number field of an item is never touched. An `exception_context` holding one is now sent with the string instead of as null. `ranetrace/ranetrace-laravel` gets the fix through the shared builders, and there is nothing to do on upgrade
- **Nothing that cannot be encoded is measured as zero bytes any more.** `Support\PayloadSizer::capBytes()` replaces an array field it cannot encode with the `_truncated` marker, with the reason `Field could not be encoded as JSON and was removed`; `Support\ItemByteBudget::cap()` treats an item it cannot encode as over budget, so that field is marked and an item still unencodable after that is dropped with an internal log line; and the worker drops an item it cannot encode from the batch it is about to send, with an internal log line naming the type and the count, and sends the rest. Before, each of them measured such a value as zero bytes and kept it, so one item could fail the encode of the whole request
- The internal log line written when a relayed JavaScript error cannot be buffered carries the message as it was built, invalid UTF-8 replaced and secrets scrubbed, where it carried the raw message, which the log lost as null when it held an invalid byte
- An error item's `file` is made relative to `project_root` only when the file is inside it. The root was stripped as a plain string prefix, so with a root of `/app` a file in `/application` was sent as `lication/...`; such a file is now sent with its full path. A root given with a trailing slash works the same as one without
- A JavaScript error's `line` or `column` that no integer can represent, such as INF, NAN or a float past the integer range, is sent as null, without the warning PHP 8.5 raises when such a float is cast to an integer. Only a host that hands the relay a PHP array can produce one; a JSON body cannot

## [1.0.7] - 2026-10-02

### Added
- **An error item carries the context the throwable itself carries, as `exception_context`.** When a throwable has a public `context()` method returning a non-empty array, as Laravel's exceptions and many of a developer's own do, that array is sent with the error: objects, closures and resources flattened, secret keys and secrets in URL values masked, at most 50 top-level keys, 3 levels deep (a deeper value becomes `[Max depth exceeded]`), string values of at most 500 characters, and at most 8,192 bytes JSON-encoded, reached by dropping trailing top-level keys. Otherwise the key is null, including when `context()` throws, which never costs the error itself. The error item is 20 keys now. The Ranetrace backend accepts the key; a backend that predates it rejects every error batch that carries it. `ranetrace/ranetrace-laravel` gets the key through the shared builder

### Fixed
- **A captured string that is not valid UTF-8 no longer costs the item it is in.** The wire is JSON, and `json_encode` refuses the whole value when one string or one array key in it holds an invalid byte, as a database driver message in latin1 does. The file buffer then failed to write, so the item was dropped with an internal log line, and in a host whose buffer does not encode, the batch carrying it could not be sent at all and was re-buffered and paused on every run. Every string the shared item builders put in an error, log, event or JavaScript error item, array keys and nested values included, now has each invalid sequence replaced by U+FFFD, through the new `Support\Utf8`. It runs before scrubbing and before the caps, so every cap still holds on the text that is sent, and it never touches the process-wide `mb_substitute_character()`. Some fields used to get a `?` in place of such a byte from the `mb_*` functions that trim and cut them, source lines and over-long values among them, and now get U+FFFD like the rest. An `exception_context` with an invalid byte is now sent with U+FFFD instead of as null; it is still null when it holds a float JSON cannot spell, such as `INF`. Payload shapes are unchanged. `ranetrace/ranetrace-laravel` gets the fix through the shared builders, and there is nothing to do on upgrade

## [1.0.6] - 2026-10-02

### Added
- `Support\DeviceType::fromUserAgent(?string $userAgent)` says what kind of device a user agent comes from: a string-backed enum whose four values, `mobile`, `tablet`, `desktop` and `console`, are the ones the backend takes for a visit's `device_type`. It gives null for a null or empty user agent; any other string is classified, and one no rule recognises is `desktop`. Consoles are checked first, tokens are matched case-sensitively and never inside a longer word, and it reads at most the first 1024 characters of the user agent. An iPad on iPadOS 13 or later is `desktop`, because its browser sends the same user agent as Safari on a Mac. `ranetrace/ranetrace-laravel` uses it for the device type of a visit

## [1.0.5] - 2026-10-01

### Changed
- **No item carries a user value the backend would reject.** The backend takes a user id only as an int or a string of at most 255 characters, and an error item's user email only as a string of at most 255 characters; one item outside that rejects its whole batch. An error item's `user` is now sent only when the host's `user_resolver` reports such an id, where before the id was passed through as it came, and its `email` only when it is such a string (null otherwise, and still only with `errors.capture_user_email` on). An event item's `user` and a JavaScript error item's `user_id` get the same check on the id, whether it came from the resolver or as an explicit argument. The check lives in `Support\UserId` and runs in the shared `Events\EventItemBuilder` and `JavaScript\ErrorItemBuilder`, so `ranetrace/ranetrace-laravel` gets it too. Nothing to do on upgrade unless your user ids can be something else, in which case those items stop carrying a user until they are an int or a short enough string

## [1.0.4] - 2026-09-30

### Added
- **Every JavaScript error item now names the browser it came from.** `browser_info` carries two more keys, `name` and `version`, so it is exactly nine keys: the seven the browser reports, then these two. They are derived on the server from the user agent the host observed, never read from the browser payload, so a tampered payload cannot set them: its own `name` or `version` is dropped and replaced. `name` is one of `Edge`, `Opera`, `Samsung Internet`, `Firefox`, `Chrome` or `Safari`. `version` is the major version as a string (`"140"`), except Safari's major.minor (`"17.6"`), because Safari ships web-platform features in point releases. Both are null for any other user agent, for a crawler that also claims Chrome (Googlebot does), for headless Chrome, and when there is no user agent at all. The browser capture script is unchanged, so there is nothing to rebuild and nothing to do on upgrade. `ranetrace/ranetrace-laravel` gets the same two keys through the shared builder
- `Support\BrowserIdentity::fromUserAgent(?string $userAgent)` is where the name and version come from: a readonly pair of `?string $name` and `?string $version`. It reads at most the first 1024 characters of the user agent, and a version longer than five digits is treated as no version, so a crafted header cannot put arbitrary text on the wire

## [1.0.1] - 2026-09-17

### Changed
- **The browser capture script is minified, so it drops from about 13.4 KB to about 4.3 KB, and from 4.0 KB to 1.7 KB over the wire.** It is inlined into every page view of every site that installs either SDK, so its comments and indentation were being downloaded by every visitor on the critical path of a page they were waiting for. With a real runtime config substituted, what `CaptureScript::withConfig()` returns goes from 13925 to 4812 bytes, 4197 to 1974 gzipped. **Behaviour is unchanged**: the same listeners, headers, breadcrumbs, deduplication, keepalive trim ladder, `window.Ranetrace` API and config keys. Nothing to do on upgrade and nothing to install: the minified file is committed and ships in the Composer package, because Composer runs no JavaScript toolchain and no consumer may need node. `resources/js/error-tracker.js` still ships as well and is the readable source of exactly the same script, which is the file to open when working out what it does. The one thing to know is that **every local variable and function in the script is renamed now**, so anything of yours that recognised the script by one of those names, or by a phrase from its header comment such as `Ranetrace JavaScript Error Tracking`, has to key on something minification keeps: a string literal, a property name, a config key, or `window.Ranetrace.captureError`
- Maintainer note: edit `resources/js/error-tracker.js`, then run `composer build-js` (`bin/build-capture-script`). It runs a pinned esbuild command (`esbuild resources/js/error-tracker.js --minify --target=es2020 --charset=utf8 --legal-comments=none --outfile=resources/js/error-tracker.min.js`, esbuild 0.28.2), verifies the output before stamping anything, and writes `resources/js/build-manifest.json` with the sha256 of both files, the version and the command. The suite compares both hashes on every run, so a source edit without a rebuild, or a hand-edit of the generated file, fails a test that names the command instead of shipping a stale script. A hash comparison is deliberately all the guard needs: the suite runs everywhere, the build runs only on a maintainer's machine. The target is `es2020` because that is exactly what the source is written in, so esbuild neither lowers the syntax nor assumes anything newer than the script already required
- `JavaScript\CaptureScript::CONFIG_TOKEN` is public. The build script and the guards that pin the substitution have to name the same token the class substitutes, and a second spelling of it somewhere else is the drift this class exists to prevent
- `contract/items/errors.json` no longer carries a `legacy_fields` block: the backend retired the `laravel_version` error-item spelling at ingest on 2026-08-21, so the fixture describes exactly the 19 keys the allow-list accepts. The `extra_vocabulary` note in `items/logs.json` and `contract/CHANGELOG.md` record both moves as applied on both sides. No code changed

## [1.0.0] - 2026-08-20

### Added
- **This package is now the one home of the four wire payload shapes, the endpoint table and the response matrix.** `ranetrace/ranetrace-laravel` builds its error, log, event and JavaScript-error items here instead of keeping a second description of the same field sets, addresses its batches from the same table, and reads the same per-status decisions. Two descriptions of a strictly-matched field set eventually disagree, and the disagreement surfaces as a backend 422 that discards a whole batch rather than as a failing test in either repo
- `Http\Endpoint` and `Http\EndpointTable`: where each capture type's batch goes, which key the body wraps it under, which feature name attributes it, and which config key holds its timeout. `EndpointTable::contract()` is the four types `contract/endpoints.json` names, and `with()` lets a host append one of its own (the Laravel SDK adds its analytics `page_visits`, which is not part of the shared contract). The SDK name is deliberately NOT in the table: it is per SDK, not per endpoint, so `Endpoint::userAgent('PHP')` and `Endpoint::userAgent('Laravel')` build `Ranetrace-PHP/Errors/1.0` and `Ranetrace-Laravel/Errors/1.0` from one shared feature name
- `Http\ResponsePolicy`, `Http\BatchOutcome`, `Http\BatchCounters` and `Http\PauseScope`: the response matrix as data. One authority answers, per status, whether the batch goes back on the spool, what pauses and for how long, whether the items are terminal, and what the 200 counters and `unprocessed_indexes` mean. `Worker\Worker` consumes it, and so does the Laravel SDK's queued batch job. `BatchOutcome::$transient` is the seam between their two shapes: this package has no queue to release to, so a transient failure pauses on the spot and the next run is the retry, while the Laravel job spends its 60/300/900s envelope first. Both land on the same pause, which is the half the contract fixes
- `Errors\ErrorContext`: everything about the host an error item needs and a throwable does not carry. `fromServer()` derives it from a `$_SERVER`-shaped array, which is all a plain PHP host has; `provided()` takes each value as stated, which is what a framework adapter has. The values are RAW, so truncation, masking and redaction stay in one place and the two SDKs cannot bound the same field differently
- `Errors\PayloadBuilder` redacts the secret-bearing path segments of the reported URL and of the `Referer`, when the host can name them. A path segment carries no marker saying it holds a token and this package has no router to ask, so the values stay the caller's to supply: `ErrorContext::provided()` takes the current request's, plus a resolver for the `Referer`, which describes a request that is NOT the one being reported and so has to be matched separately. A host that cannot say keeps the previous query-only behaviour
- `Logging\LogItemBuilder`, `Events\EventItemBuilder` and `JavaScript\ErrorItemBuilder`: the three remaining item shapes, lifted out of the handler, the tracker and the relay so both SDKs compose the same keys, caps and markers. The event and JavaScript-error fingerprints arrive already hashed rather than being computed there: the builder is handed a finished observation of a request, not the request itself. `Support\FingerprintGenerator` is where both SDKs derive them
- `Support\Scrubber` and `Support\Diagnostics`, the two collaborator interfaces the shared builders take, so the builders depend on the capability rather than on a class. `SecretScrubber` and `InternalLogger` implement them, so nothing changes for this package; the Laravel SDK keeps its own `Diagnostics`, which writes to its dedicated log channel rather than to a file under the buffer directory
- `JavaScript\CaptureScript::withConfig()`, the seam that makes this package the one home of the browser capture script. It returns the bare script body with a caller-supplied runtime config substituted into it, and deliberately no `<script>` tag: the tag's attributes are the host's business, since this SDK takes a nonce as an option while the Laravel SDK asks `Vite::cspNonce()` for one. `ranetrace/ranetrace-laravel` carried a byte-identical copy of the same ~370 lines inline in `error-tracker.blade.php`, and because each SDK's relay validates exactly what its own copy sent, a fix applied to one silently stranded the other: nothing failed until a browser posted a shape the other relay did not accept. Both SDKs now render `resources/js/error-tracker.js`, each supplying its own config
- The capture script can send an `X-CSRF-TOKEN` header, when and only when the host puts a `csrfToken` in the config. The Laravel SDK's relay sits behind CSRF middleware and needs it; this SDK's relay verifies `Origin`/`Referer` instead and supplies no token, so nothing about what this SDK's script sends has changed. A capability only one host has now lives behind config rather than in a forked script, which is the rule for anything the two hosts do differently. A blank token counts as no token: it means no session was started, and an empty header would fail the check anyway
- Every captured item is held to a per-item byte budget on its way to the buffer: 70 KB JSON-encoded per item, 8 KB per field. Ported from `ranetrace/ranetrace-laravel` (`BaseRanetraceJob::capItemBytes()`) and already recorded as `client_item_policy` in `contract/envelope.json`, which the contract suite now asserts the constants against. An item within the budget is untouched. Over it, every string field above the per-field budget is cut and suffixed `... (truncated)`, and every array field above it is replaced wholesale, because truncating a structure mid-way yields invalid JSON. The capture paths already cap their own fields, but they cap characters where the API weighs bytes, and they cap fields one at a time where the budget is per item: twenty breadcrumbs of 5 KB each is 100 KB with no single cap exceeded. Without the budget one such item sits in the buffer until the worker sends it, and because the batch trimmer always keeps at least one item (a single item cannot be split) it draws a 413 that discards the whole batch and pauses the feature for fifteen minutes
- An item still over budget after shrinking is dropped outright and the loss is written to the internal log, under a message distinct from the shrink one. It is deliberately NOT replaced with a marker payload: the wire shape is an allow-list per type, so a top-level marker key belongs to no type, and on the errors endpoint strict field matching would reject the item and take the whole batch of up to a thousand items with it, which is the exact failure the budget exists to prevent. Losing one item is cheaper. The nested `_truncated` marker inside a free-shape field (log `context` and `extra`, JavaScript-error `context`, breadcrumb `data`) is a different thing and is unchanged
- The policy lives in one class, `Support\ItemByteBudget`, applied at each of the four buffer handoffs (errors, events, logs, JavaScript relay). This SDK has no base job to hook the way the Laravel SDK does, and the buffer implementations stay generic on purpose, so the four call sites share the class rather than each repeating the policy or it being buried in `FileBuffer`. It runs after scrubbing, so cutting a string cannot expose a secret past a redaction
- **This package is now the one home of `SecretScrubber`, `PayloadSizer` and `FingerprintGenerator` as well.** `ranetrace/ranetrace-laravel` deleted its copies of all three, along with the `CoreScrubber` bridge that stood in for the merge. Redaction and fingerprint derivation are promises to the same backend from two SDKs, and the copies had already drifted: nine test cases apart in the scrubber suites, and a fingerprint salt that fell back to `APP_KEY` on one side and to the API key on the other
- `SecretScrubber::scrubDeep()` and `scrubUrlPath()` take a CALLABLE for `$sensitiveValues`, alongside the fixed list and null they already took. A callable is asked, per URL-shaped value, which of that URL's path segments hold a secret. This is what the Laravel SDK needed and a single pre-resolved list could not give it: free-form data (breadcrumbs, log context, event properties) carries URLs from requests other than the one being handled, and one shared list would redact the wrong URL's secret. Hosts passing a list or nothing are unaffected. A callable that throws is caught, logged and treated as "cannot say", because it is host code reaching for a router in the middle of a capture
- `Logging\LogItemBuilder::build()` takes the same `$sensitivePathValues` argument the event and JavaScript-error builders already took, so a host with a router can have path secrets redacted from log context and `extra` too. It defaults to null, which is the previous query-only behaviour and the right answer for a host with no router

### Changed
- **`Errors\PayloadBuilder::build()` takes an `ErrorContext` where it took `array $server, bool $isConsole`.** `ErrorContext::fromServer($server, $isConsole)` is the same thing for a plain PHP host, and `ErrorReporter` passes it, so nothing about what this SDK captures has changed. The class is internal to the capture path and no documented wiring calls it directly
- `Worker\Worker`'s private endpoint table and its `PAUSE_SECONDS` / `RATE_LIMIT_FLOOR_SECONDS` constants moved to `Http\EndpointTable` and `Http\ResponsePolicy`. The worker's behaviour, its diagnostics wording and its pause lengths are unchanged; the contract suite now asserts the shared classes against `contract/endpoints.json`, `contract/headers.json` and `contract/responses.json` row by row, where before it read the worker's constants through reflection
- `SecretScrubber` and the shared builders type-hint `Support\Scrubber` and `Support\Diagnostics` rather than the concrete classes. `SecretScrubber implements Scrubber` and `InternalLogger implements Diagnostics`, so every existing call site keeps working
- `JavaScript\Snippet` no longer reads or substitutes the script template itself. It builds the runtime config from `Config` and hands it to `CaptureScript`; the rendered `<script>` tag is unchanged apart from the endpoint URL keeping its slashes unescaped, which is safe because `JSON_HEX_TAG` escapes the `<` of a `</script>` on its own and never relied on the slash

### Fixed
- `SecretScrubber::scrubString()` no longer backtracks super-linearly, so the PCRE give-up it used to provoke is now practically unreachable. The pattern's leading `[\w.\-]*` re-tried every prefix length at every start position, which on a long run of word characters (a stack trace, a base64 blob in a log message) is quadratic: a 50k run cost billions of steps and ended at the backtrack limit, where the whole value was redacted wholesale. Three changes make it linear. A `(?<![\w.\-])` guard means a match can only start where a key token can, so a long run is entered once instead of once per character; the prefix is bounded to 64 characters, which is far more than any real key name has before its sensitive fragment; and the suffix is possessive, since the separator characters it would give word characters back for are all outside the class, so that backtracking never helped. A 50k adversarial input now completes in well under a millisecond and gets the precise redaction instead of losing the whole string. Fail-closed behaviour is unchanged and still covered: PCRE can still give up on bad UTF-8 or a host-lowered `pcre.backtrack_limit`, and the value still becomes `[REDACTED]` with a line in the internal log. The one case the new spelling gives up on deliberately is a sensitive fragment buried more than 64 characters into a single unbroken token

### Security
- URL values inside breadcrumbs, log context and event properties are now recognised by their **shape** rather than by an `http(s)://` prefix. Previously a relative URL passed through untouched, so a signed download link recorded as `/exports/42/download?expires=…&signature=…` shipped its signature while the identical absolute URL was redacted. The shape test is deliberately strict (no whitespace, none of the characters that only turn up in prose, JSON and code, and a query that is a run of `key=value` pairs) because the redaction rewrites the query, and the fragment when that is query-shaped too, and a looser test would truncate a JSON log-context payload mid-structure. A value that fails the test is left byte-for-byte alone
- `SecretScrubber::scrubDeep()` takes the host's declared sensitive path segments and redacts them inside URL-shaped values, so a reset link the tracker recorded as a navigation breadcrumb loses its `{token}` the same way the top-level `url` field already did. Without it the same payload redacted the secret in one field and shipped it in another. A path segment carries no marker saying it holds a token and this SDK has no router to ask, so the values stay the caller's to supply: `Relay` and `EventTracker` pass whatever was given to their `setSensitivePathValues()`, and passing nothing keeps the previous query-only behaviour. This SDK's Monolog handler names none, so its log context stays query-only; a host that can name them passes them to `LogItemBuilder::build()`
- The JavaScript error `message` is scrubbed the way the sibling `stack` field already was. The bundled snippet's `unhandledrejection` handler `JSON.stringify`s the rejection value into `message`, so a rejected API response carrying an `api_key` reached the backend in full while the same text inside `stack` was redacted
- The JavaScript error relay's `timestamp` and `breadcrumbs.*.timestamp` fields are capped at 64 characters. They had no length rule and nothing downstream bounded them, so an unauthenticated client could buffer an item limited only by `post_max_size`, large enough to draw a 413 that discards the whole batch and pauses JavaScript error capture

- `SecretScrubber::scrubString()` now fails closed. Its pattern backtracks super-linearly on a long run of word characters, so PCRE can hit its backtrack limit and give up; the method then returned the input, shipping the exact string it had been asked to redact. It now returns `[REDACTED]` for the whole value and writes `preg_last_error_msg()` to the internal log, so a scrubber that has started swallowing strings is visible rather than silent. Losing the string beats leaking it
- The URL fragment is scrubbed. `scrubUrl()` copied it through untouched and `scrubUrlPath()` stopped at the first `?` or `#`, so both shapes of fragment secret survived: the query-shaped `/callback#access_token=…&expires_in=…` an OAuth implicit-flow redirect comes back as, and the path-shaped SPA hash route `/app#/reset/{token}`. A fragment that is query-shaped, judged by the same strict `key=value` run the relative-URL shape test uses, now goes through query scrubbing, and any fragment goes through path-segment scrubbing, which only replaces a segment that exactly equals a declared sensitive value. A fragment of any other shape, an anchor such as `#section-2`, comes back byte-for-byte
- `scrubUrlPath()` recognises a URL's scheme only at the start of the string. It searched for `://` anywhere, so a relative URL carrying an unencoded absolute one in its query or fragment (`/reset-password/{token}?next=https://app.test/dashboard`) put the path window inside the query, inspected the wrong substring as the path, and shipped the live token. The anchored match also covers the protocol-relative `//host/path` form, which used to be read as a path and is now read as an authority
