# Changelog

All notable changes to `ranetrace-php` will be documented in this file.

This file starts here, so releases before it are not recorded; the git history is the record for those.

## [Unreleased]

### Changed
- **An event tracked from a console process sends no session hash.** A command, a cron script or a queue worker has no visitor, but its events carried a `session_id_hash` built from an empty address, an empty user agent and the date: one value for every console event of the day. Ranetrace counts the sessions of events without a user as visitors, so a day of scheduled events showed as one active user. `session_id_hash` is now null there, as `user_agent_hash` already was, and both are null in a console process whatever the server context holds. An event tracked in a request is sent exactly as before. `Events\EventItemBuilder::build()` takes a nullable session hash. The API already accepts null for the field, so there is nothing to do on upgrade. Active users on the events page no longer counts events from console processes that name no user

### Fixed
- **A Telegram bot token no longer leaves the host inside a message, a trace or a logged value.** Every Telegram Bot API request carries the bot token in the path of its URL, `https://api.telegram.org/bot<id>:<token>/sendMessage`, and an HTTP client puts that URL in the message of a failed request: Guzzle's `Client error: POST https://api.telegram.org/bot...` and `cURL error 28: ... for https://api.telegram.org/bot...`, which a notification channel then wraps in an exception of its own. Nothing redacted it, because no key names it and it has no prefix, so a failed send stored the token in the error's message, in the message of each previous exception and in a log record of the same failure, readable by everyone who can read that website's errors, the agents connected through the MCP server included. It is now redacted by its value: whatever follows `bot` on `api.telegram.org`, also under `/file/`, up to the next `/`, a `/bot<id>:<token>` segment on any other host, such as a self-hosted Bot API server, and a token that stands on its own, in a message, a trace, a source line and every string value of log context, event properties, breadcrumbs and an exception's `context()`. The URL arrives as `https://api.telegram.org/bot[REDACTED]/sendMessage`. **If your application sends through a Telegram bot and one of those requests has ever failed, treat the token as exposed:** look for `api.telegram.org` in your errors and logs in Ranetrace, delete what you find, and issue a new token with BotFather's `/revoke`. Connected chats keep working, because they belong to the bot and not to the token
- **The secret part of a Slack or Discord incoming webhook URL no longer leaves the host inside a message, a trace or a logged value.** Like a Telegram Bot API URL, a webhook URL is its own credential, and an HTTP client puts it in the message of a failed request. `https://hooks.slack.com/services/T.../B.../...` now arrives as `https://hooks.slack.com/services/[REDACTED]`, as do that host's `workflows` and `triggers` URLs, and `https://discord.com/api/webhooks/<id>/<token>` arrives as `https://discord.com/api/webhooks/<id>/[REDACTED]`, on `discordapp.com` and with an API version in the path as well. If one of those requests has ever failed in your application, look for `hooks.slack.com` and `discord.com/api/webhooks` in your errors and logs in Ranetrace, delete what you find, and replace the webhook
- **A token with a known prefix is redacted when it is written percent-encoded inside a URL, or stands right after an encoded character.** The value pass that recognises a Stripe `sk_live_` key, a GitHub or GitLab token, a Slack token, an AWS access key id or a JWT wherever it stands read raw text only. A token whose `_`, `-` or `.` was written as `%5F`, `%2D` or `%2E`, as in `/keys/sk%5Flive%5F...`, was sent as written, and so was a token behind an encoded separator, as in the URL inside `?next=https%3A%2F%2Fapp.test%2Fkeys%2Fsk_live_...`, because the `F` of `%2F` read as the letter before it. Both are now redacted in a message, a trace, a source line and every string value of log context, event properties, breadcrumbs and an exception's `context()`. Nothing to do on upgrade

## [1.2.1] - 2026-11-13

### Fixed
- **The END marker of a private key is found on PCRE2 10.45 to 10.47.** Under JIT, those PCRE2 versions can miss a match of a pattern shaped like the one that finds `-----BEGIN ... PRIVATE KEY-----` and `-----END ... PRIVATE KEY-----` in source lines, and they missed every END marker. In a source window that holds the BEGIN marker, the END line and every line after it in that window were redacted as key body, which cost readable code and no secret. In a window that starts inside a key, nothing said that the lines above the END marker are body, so a body line under 40 characters, such as the last line of a key, was sent as written; a full-length body line was still redacted. The pattern now has a form those versions match, and it matches exactly what it did. PHP's bundled PCRE2 is 10.44 and not affected. A PHP linked to a system PCRE2 is when `php -r 'echo PCRE_VERSION;'` prints 10.45, 10.46 or 10.47. Nothing to do on upgrade

## [1.2.0] - 2026-11-13

### Added
- **`vendor/bin/ranetrace-test` checks the install.** It captures one test error (`Test exception from Ranetrace`) and one test event (`test_event`, with `source: ranetrace-test`), sends each straight to the API, and prints what the API answered per type, then the buffer path, the items waiting in it and any pauses. It exits `0` when the API accepted at least one of the two, and `1` otherwise, so a missing key, a refused key and an unreachable API no longer all look like success. The test items go beside the buffer, never into it, and no answer sets a pause, so a failed test leaves nothing behind. A 200 lifts the pauses it disproves: a pause on everything after a 401, and that type's own pause unless the API set it with a 429, 413 or 422. Like `ranetrace-flush`, the binary reads the environment only; an application that configures the SDK in its bootstrap runs the same check from its own console with `Ranetrace::instance()->sendTest()`, which returns a `Worker\TestReport` (`accepted()`, `render()`). The API stores an identical error once per 5 minutes, so a second run within 5 minutes reports the error as accepted, not stored. The items carry no field the API would not expect. Nothing to do on upgrade

### Changed
- **The absolute path of your project no longer leaves the host inside a text.** An error's `file` and its frames were already sent relative to `project_root`, but a path inside a text was sent as written: Laravel's `(View: /var/www/app/resources/views/profile.blade.php)` at the end of a view error's message, the `PATH ... ENDPATH` comment a compiled Blade view ends in when it is near the failing line, every frame line of the `trace` string, a console command started as `/var/www/app/artisan`, and a logged exception, whose string form holds its file and whole trace. `Support\ProjectRootStripper` now takes the root off every path under it in an error's `message`, `trace`, source lines, `console_command`, `console_arguments`, `exception_context` and each previous exception's `message`, and in a log record's `message`, `context` and `extra`, so that message arrives as `(View: resources/views/profile.blade.php)`. The root named on its own, with nothing under it, becomes `[project root]`. It is matched only where a path starts, so a root of `/app` leaves `/var/app/x.php` alone, under either separator and inside JSON-escaped text. A path outside the project root is sent as written, as before. A console command started through a symlinked deployment, such as `/home/forge/site/current/artisan schedule:run` where `current` points at the release PHP runs from, has its script path resolved to the release first, so it arrives as `artisan schedule:run` in `console_command` and as `artisan` in `console_arguments`; a relative script path, or one that does not resolve, is left as typed. Three limits: any other text that names the project through such a symlink keeps that path, which is not recognised; a URL path that starts with the root (`GET /app/users` where the root is `/app`) reads as a file under it; and with `zend.exception_ignore_args` off, a frame line of the `trace` string cuts a string argument to 15 characters, so a root passed to a call can arrive as its start, `('/home/forge/sit...')`. A strip that cannot run, such as a pattern the host's PCRE refuses to compile, leaves the text as written and says so once in the internal log: it never costs the capture or its secret scrub. No field changes shape. Nothing to do on upgrade
- **An error whose class is anonymous is typed without the absolute path, the NUL byte and the counter PHP puts in its name.** PHP names the class of `throw new class extends RuntimeException {}` `RuntimeException@anonymous`, then a NUL byte, the absolute path of the file that declares it and `:line$0`. The error's `type` carried that name as it was, so the server's path left the host, a NUL byte landed in `type`, and a long enough path took `type` past its 255 character maximum, which got the whole report refused. The `type` is now built like a previous exception's: the project root comes off, the NUL becomes a space, the counter after the line goes, and it is cut to 255 characters, so it reads `RuntimeException@anonymous app/Jobs/Import.php:3`. The counter is the number of anonymous classes the process compiled before this one, so it could differ after a deploy or a PHP restart. It also goes from a frame's `class` and `function` and from a previous exception's `type`, which carried it too. An ordinary class name is sent exactly as before. **Existing groups of anonymous-class errors split once on upgrade**, because the backend groups errors by `type` together with file, line and environment, so the first such error after the upgrade starts a new group. It is still the better key: on a deployment that changes its release directory on every deploy, that directory was part of the type, so these errors started a new group on every deploy, and the counter could start one after any restart. The type now changes only when the class moves to another line. Nothing to do on upgrade
- **`vendor/bin/ranetrace-flush` exits 1 with one line on stderr when it cannot use the buffer, and the buffer is for one user.** The SDK's texts promised a buffer directory created `0770` that a web process and a cron flush running as different members of one group could share, but `mkdir` applies the process umask and nothing changed the mode afterwards: under the usual `022` the directory is `0750` and its files `0644`, so the group could not write. A flush run as a user other than the web server's then drained nothing, could not write the internal log, which lives in the same directory, and exited `0`, so nothing told you. The internal log also created the directory `0775` when it got there first. The buffer is now documented as one user's: run the flush as the user the web server runs as. The SDK does not force a mode against the umask, and the internal log creates the directory with the same mode as the buffer. When this process cannot use the spool, because the buffer path is not a directory it can write to, a lock file it cannot write or a buffer file it cannot read, the flush still drains what it can and then exits `1` with `ranetrace-flush: cannot write to the buffer in [/path] as user [deploy]: the lock file errors.lock is not writable. Run this command as the user your web server runs as.` (the user name only where ext-posix is loaded). The documented cron line discards output, so the README and `AGENTS.md` now say to run the command once by hand as the cron job's user to check it. `Buffer\FileBuffer::accessProblem()` gives the reason, or null, and creates nothing. A missing buffer directory, an empty buffer and a lock another process holds are not problems. On upgrade: nothing to do when the cron job already runs as the web user. Otherwise move it to that user's crontab
- **An event tracked without a user agent sends `user_agent_hash` as null, where it sent an empty string.** Every event from a console process has no user agent. The API takes the field as null or 64 characters, and accepted the empty string only because the backend turns empty strings into null before it validates. `Support\FingerprintGenerator::generateUserAgentHash()` now returns `?string`, null for a missing user agent, and `Events\EventItemBuilder::build()` takes a nullable hash. Nothing changes in what Ranetrace stores. If you call `generateUserAgentHash()` yourself, expect null where you got `''`.

### Fixed
- **A flush without an API key no longer pauses the process that has one, and `vendor/bin/ranetrace-flush` says the key is missing.** `ranetrace-flush` reads the environment only, and a plain PHP site often loads its key from `.env` in its bootstrap, so the web process had the key and the cron job did not. The keyless cron flush took the waiting items, read the missing key as a network failure, put the items back and wrote a 15 minute pause into the pause store the web process shares, so the web process stopped sending too. The command printed nothing and exited `0`, and the internal log said `Network error during batch send`. A flush without a key now takes nothing from the buffer and neither reads nor sets a pause, and the internal log says `Skipping run, no API key is configured` with the waiting types when something waits (and nothing when the buffer is empty, so a keyless development site gets no line per request). `ranetrace-flush` then exits `1` with `ranetrace-flush: RANETRACE_KEY is not set in this command's environment, so nothing is sent. This command reads the environment only: a key your application loads from a .env file or sets in its bootstrap does not reach it. Set it in the cron job's environment.` on stderr, before the buffer access line when that applies as well. A site switched off with `RANETRACE_ENABLED=false` and nothing waiting stays quiet and exits `0`. `contract/responses.json` states the behaviour as `without_api_key`. On upgrade: when the cron mailer reports this line, set `RANETRACE_KEY` in the cron job's environment
- **A capture whose secret scrub fails is sent redacted, also on a host that turns PHP warnings into exceptions.** When PCRE cannot compile the scrub pattern it says so with a warning. `SecretScrubber` caught only its own give-up, so on a host whose error handler throws on a warning, as Laravel's and Symfony's do, the exception escaped the scrubber and the whole error report, log record or browser error was dropped, with a line in the internal log as the only trace. One way to get there is a list of `scrubbing.extra_keys` too long for one pattern, from about 500 entries. `scrubString()`, `scrubSource()` and the value pass of `scrubDeep()` now fail closed on whatever is thrown: the string, the source window or the value becomes `[REDACTED]`, the internal log says so, and the item is sent with its type, file, line, level and every other field intact. Nothing to do on upgrade. An error whose message reads `[REDACTED]` means the scrubber is failing on your host: the internal log names the cause
- **An event or a browser error is captured when your `user_resolver` throws, without a user.** The resolver is host code, such as a session store or an auth guard, and it can throw when the host is already in trouble. An error report already lost only its user then, but an event was dropped whole, with `Failed to track event` in the internal log, and the JavaScript error relay answered the browser 500 `Failed to process error` and buffered nothing. `Support\UserResolver` now asks the resolver for all three: a throw costs the item its user (`user` or `user_id` is null), the item is buffered as usual, the relay answers 200, and the internal log holds one `Ranetrace user resolver failed` warning with the exception message. A resolver that does not throw is read exactly as before. Nothing to do on upgrade

## [1.1.2] - 2026-11-10

### Fixed
- **A resource that fails to load is no longer reported as an error named "Unknown error".** The browser script listens for `error` in the capture phase, so it also received the event a browser fires on a script, stylesheet or image that failed to load. That event carries no message, file, line or error object, and the script sent it under the name "Unknown error": a tag manager blocked by an ad blocker filed one empty report per page view. The script now reports an `error` event only when it was fired on `window`, which is where a script error is fired. An event without a message of its own takes the message of its error object, and one with neither is dropped instead of being given a name. If you added `'Unknown error'` to `javascript_errors.ignored_errors` to keep these reports out, remove it: the list matches on part of a message, so that entry also hides every real error whose message contains those words. Nothing else to do on upgrade

## [1.1.1] - 2026-10-16

### Fixed
- **Scrubbing works on PHP linked to a PCRE2 older than 10.43.** 1.1.0 built a pattern that only PCRE2 10.43 and later can compile, and PHP is often linked to an older system PCRE2 (Ubuntu 22.04 and 24.04, Debian 12). There, every free-form scrub failed to compile, so error reports, logs and JavaScript errors were not captured. The pattern now compiles on every PCRE2 and redacts exactly what it did before. Nothing to do on upgrade
- **Scrubbing a line of many sensitive calls takes time in proportion to its length.** After each sensitive call, such as `$client->setToken('a')` or a PDO subclass's `parent::__construct('a')`, the check for a fallback behind its `)` made PCRE2's JIT search the rest of the text for a `?` first. So a line of many such calls took time quadratic in its length: ten source lines of 5,000 `parent::__construct('a');` took 1.2 seconds on PCRE2 10.42, and newer PCRE2 was slower to show it but not immune. The check now looks only where it stands, and what is redacted is unchanged. Nothing to do on upgrade

## [1.1.0] - 2026-10-16

### Added
- **Errors carry structured stack frames, source lines around them and the chain of previous exceptions.** The error item gains `frames`, `frames_omitted` and `previous` (23 keys, up from 20), as `contract/items/errors.json` describes. Each frame is the trace's `file`, `line`, `class`, `function` and call `type`, with paths relative to `project_root`, absolute paths inside closure and anonymous class names made relative too, and `is_vendor` set for a file under `{project_root}/vendor`. A frame in your own code carries the lines around it (up to five either side, at most 2,015 characters each, dedented and secret-scrubbed) as `source`; a vendor frame carries none. A trace longer than 50 frames keeps its 40 innermost and 10 outermost and counts the rest in `frames_omitted`. Up to 5 previous exceptions travel, nearest first, each with its type, scrubbed message, throw site, the source lines there (vendor or not) and its own frames; a chain that loops back stops at the first repeat, and a failure while it is read costs the chain, never the report. **Frames never carry argument values**: a frame's `args` are not read at all, whatever `zend.exception_ignore_args` says. The `trace` string is unchanged, PHP's own `getTraceAsString()`. Each source file is read at most once per error, and only a regular, readable file under 1 MB that is not eval'd code
- **`errors.capture_source` (`RANETRACE_ERRORS_CAPTURE_SOURCE`), default `true`.** Set it to `false` to send no source line at all: every frame's `source` is null, and so are the error's existing `context` and `highlight_line`
- **Some secrets are caught by their value, not only by the name they sit under.** `SecretScrubber::scrubString()` and `scrubSource()`, which scrub error and log messages, traces, console arguments, browser error messages and source lines, now redact the password in a URL wherever it stands and keep the scheme, user name and host: `$dsn = 'pgsql://app:Pw0rd@db/app'` arrives as `$dsn = 'pgsql://app:[REDACTED]@db/app'`, `redis://:pw@cache:6379` as `redis://:[REDACTED]@cache:6379`, and a JSON-encoded URL (`pgsql:\/\/...`) is read the same way. The password runs to the last `@` before the host, so an unencoded `@` in it does not leave half of it behind. They also redact, whole, a token whose prefix says it is a credential: Stripe live secret and restricted keys (`sk_live_`, `rk_live_`), AWS access key ids (`AKIA`, `ASIA`), GitHub tokens (`ghp_`, `gho_`, `github_pat_`), Slack tokens (`xoxa-`, `xoxb-`, `xoxp-`, `xoxr-`), GitLab personal access tokens (`glpat-`) and JWTs. The list is short on purpose, since each prefix must start nothing but a credential: a Stripe publishable or test key, an identifier such as `$sk_live_mode` and a prefix with too short a body stay readable. `scrubDeep()`, which scrubs log context and extra, event properties, breadcrumbs and an exception's `context()`, runs the same value pass over every string in them, so `['dsn' => 'pgsql://app:Pw0rd@db']` loses its password under a key that says nothing; a value whose pass fails is replaced by `[REDACTED]` on its own and the internal log says so. `scrub()` stays key-based. `pwd` joins the built-in key fragments, so `$pwd = '...'`, a `db_pwd` key and `CURLOPT_USERPWD => '...'` are redacted, at the cost of a `PWD` environment variable a host logs itself. `pass` and `dsn` do not join: most names that hold them are not secret (`passes`, `bypass`, `compass`, `recordsNotFound`), as the `SecretScrubber::DEFAULT_KEYS` docblock records with the counts. Any other secret under a name the fragment list does not hold, such as `$pin = '4821'`, is still sent as written; `scrubbing.extra_keys` adds names. Nothing to do on upgrade
- **`Errors\FrameMapper`**, an optional list passed as `PayloadBuilder`'s fourth constructor argument. Each mapper gets a frame's absolute location (`Errors\FrameLocation`, file and line) and returns the location a developer wrote, or null. Mapping happens before the path is made relative, before the vendor check and before the source is read, so a compiled template frame can arrive as its template, line and template source. It applies to frames and to each previous exception's throw site, not to the error's own `file` and `line`. A mapper that throws costs that one mapping. `ranetrace/ranetrace-laravel` will use it for compiled Blade views

### Changed
- **The error's `context` lines are secret-scrubbed** like every other source line, where before they were sent as written. A `key=value` secret on a line near the throw site now arrives as `[REDACTED]`
- **An over-budget error item sheds its frames before anything else is cut.** `Support\ItemByteBudget::cap()` hands an `errors` item to `Errors\ErrorItemShedder` first, which drops source objects (the previous exceptions' frames first, then the error's own frames from the outermost, its first app frame and the throw sites last), then frames from the middle of each list, then previous exceptions from the far end, stopping as soon as the item fits. `frames` and `previous` are never replaced by the `_truncated` marker, which the backend refuses there. Other item types are cut exactly as before
- **Breaking for a custom scrubber: `Support\Scrubber` requires `scrubSource(array $lines): array`.** `Errors\SourceReader` hands it each source window once, together with up to 50 lines above it (so up to 61 lines), as a list of lines without their line breaks, and expects exactly one line back per line, in the same order, where it called `scrubString()` per line. A window whose scrubber throws, or returns another number of lines, is dropped, and the report goes out without it. A host that implements `Scrubber` itself has to add the method; a host on `SecretScrubber` has nothing to do

### Fixed
- **Free-form scrubbing catches the secret shapes a source line holds.** `SecretScrubber::scrubString()`, which scrubs error and log messages, traces, console arguments, browser error messages and now source lines, ended a quoted value at its first space, comma or semicolon and then required the closing quote right there, so `$password = 'two words';` and `"password":"a b"` shipped whole, and `'token' => "a,b",` came out as `'token' =[REDACTED] "a,b",` with the value intact. A quoted value now runs to its matching closing quote, past escaped quotes, or to the end of its line when it has none. `=>` is never split, `==`, `===`, `!=` and `!==` count as separators, and so do the fallbacks `??` and `?:`, so `$_SERVER['HTTP_AUTHORIZATION'] ?? 'Bearer abc'` loses its fallback, and so does `$request->input('password') ?? 'default'`, where a quoted sensitive key closes a call (only before a fallback, so `strpos($x, 'token') !== false` stays readable); `::` and the `?` of a full ternary do not, and a quoted sensitive key followed by `,` and a quoted value is redacted too, which covers `define('STRIPE_SECRET', '...')` and `env('API_KEY', '...')`. A quoted dotted key whose last segment is a validation rule, such as `'password.required' => 'Vul je wachtwoord in'` in a FormRequest's `messages()`, names a message and keeps its value; `'services.stripe.secret'` and `'password.live'` do not. An `Authorization: Bearer ...` header keeps its scheme and loses its credential. Nothing to do on upgrade
- **A code value after a sensitive key keeps its code and loses only its string literals.** `SecretScrubber::scrubString()` read an unquoted value up to the first quote or bracket, so `'password' => Hash::make('x'),` came out as `'password' => [REDACTED]'x'),`, garbled and with the literal, the actual secret, left in it, and `'remember_token' => $user->getRememberToken(),` lost readable code for nothing. In a source line, a value that starts as code (a variable, an opening bracket, `new`, `fn`, or a name followed by `(`, `::` or `->`) is now kept byte-for-byte with the body of every string literal in it replaced by `[REDACTED]`, so the first becomes `'password' => Hash::make('[REDACTED]'),` and the second stays as written. A name followed by spaces and then `(`, `::` or `->`, as in `'password' => bcrypt ('x'),`, is redacted itself, since in a comment such as `password: hunter2 (old)` the word is the secret, and what follows it is read as code: `'password' => [REDACTED] ('[REDACTED]'),`. It ends at a `,` or `;` outside its brackets, at the bracket that closes around it, at a comment outside its brackets or at `?>`, or at the end of its line, so the next pair on the line keeps its value. A literal that only names where a value lives is kept: the first argument of a global `env()`, `getenv()` or `config()` call and the subscript of `$_ENV` or `$_SERVER`, when that argument is a plain string literal, so `'password' => env('DB_PASSWORD', 'x'),` becomes `'password' => env('DB_PASSWORD', '[REDACTED]'),`. The same holds among the arguments of a sensitive call, as in `$client->setToken(env('API_TOKEN'))`. In a message, a trace, a log record or a command line an unquoted value is not code (`--password=$Up3r`, `Bearer $TOKEN`): it is redacted whole as before, and a bracket in it is followed to its matching close, so `token=(abc)`, `{"token":{...}}` and `'password' => Hash::make('x')` lose the whole value, where the last used to ship `'x'`, and so does `'token' => new Foo('x')`. A quoted value and a bare token (`password=hunter2`, `null`, a number, a constant) are redacted whole as before, and a literal joined onto a quoted value with `.` (`'abc' . 'def'`) is redacted with it. A bare token also no longer ends inside a multibyte character when the host has set a UTF-8 locale with `setlocale()`, which sent invalid UTF-8. Nothing to do on upgrade
- **A subscript key and a call with a sensitive name count as keys.** `$config['password'] = 'hunter2';`, `$config["db"]["password"] = "x";` and `$_ENV['API_KEY'] = '...'` shipped their value, because the `]` between key and `=` hid the key; they are now redacted like any other pair, and `$config['password'] === $input` stays readable. A call to a function or method whose name holds a sensitive fragment, such as `Stripe::setApiKey('sk_live_...')`, `$client->setToken('...')`, `Http::withToken('...')` or `->setCredentials('user', 'pass')`, now has every string literal among its arguments redacted and the rest kept, which also covers such a call in a text trace. A fallback after such a call is its value, so `$user->getToken() ?? 'x'` and `$client->tokenFor('api') ?? 'x'` lose `'x'`, also when the fallback starts the next line; a comparison after the call (`getToken() === null`) or a chained `->value` does not make it one, and a fallback that is code (`?? abort(404)` in source) is kept. A call with no literal, such as `PersonalAccessToken::findToken($token)`, is unchanged, and so is a call whose name ends in `Exception` or `Error`, whose argument is a message the error already carries: `throw new TokenMismatchException('CSRF token mismatch.');` stays readable. Calls that take a credential by position under a name that says nothing about it are read the same way when they are on a short, curated list: `new PDO(...)` and `new mysqli(...)` (`PDO->__construct(...)` and `mysqli->__construct(...)` in a text trace), `mysqli_connect`, `mysqli_real_connect`, `->real_connect`, `ldap_bind`, `ldap_sasl_bind`, `ftp_login`, `ssh2_auth_password`, `imap_open`, and Laravel's `withBasicAuth` and `withDigestAuth`. Every literal among their arguments is redacted, the DSN, host and user name included, so `new PDO($dsn, 'root', 'hunter2')` becomes `new PDO($dsn, '[REDACTED]', '[REDACTED]')`. They match by whole name only, so `my_mysqli_connect_wrapper(...)`, `new PDOException(...)` and `auth('api')` stay readable. In a source window whose lines, or the lines read above it, declare a class that `extends PDO` or `extends mysqli`, also with the class name on a line after `extends` or after a comment, `parent::__construct(...)` is read the same way; anywhere else it stays readable, since an exception subclass hands its message on with it. Still not caught: a credential passed by position to a call on neither list, such as your own `connect($host, 'root', 'hunter2')`, unless its value is one of the shapes the entry on secrets caught by their value lists, and a value under a name the fragment list does not hold, such as `$pin = '4821'` (`scrubbing.extra_keys` adds names). If your code has such lines, set `RANETRACE_ERRORS_CAPTURE_SOURCE=false` to send no source line at all. Nothing to do on upgrade otherwise
- **A source window is scrubbed as a whole, so a secret that spans lines is caught.** Each source line was scrubbed on its own, so a value formatted onto the line after its key (`'password' =>` then `'hunter2',`) and every line of a private key shipped as written. A line that ends in a sensitive key and `=>`, `=`, `.=`, `??=` or a fallback (`??`, `?:`) now has the start of the next line scrubbed as that value, and a line that ends in a sensitive read (`$token`, `$config['password']`, `$request->input('password')`) whose next line starts with `??`, `??=` or `?:` has the value after it scrubbed; `:` and comparisons do not carry over, so `case 'token':` followed by `return $x;` stays readable. While the parentheses of a sensitive call, or a bracket opened in a code value after a sensitive key, stay open at the end of a line, the lines after it are read as the same value until the bracket closes, so `setCredentials(` with `'user',` and `'pass'` on lines of their own loses both literals and keeps its code. A comment inside the brackets is scrubbed as prose and does not end the value, so a `// note` line or a `/* note */` between two arguments costs no literal after it, and a block comment that runs over several lines is read as a comment up to its end, whatever quotes it holds, before the value goes on; a `?>` still ends it. A redacted string literal still open at the end of its line goes on being redacted up to its closing quote on the lines after it. The body lines of a heredoc or nowdoc assigned to a sensitive key, or used as the fallback of a sensitive read (`$user->getToken() ?? <<<EOT`, `$config['password'] ?: <<<EOT`, also with the `??` starting the next line), are redacted up to its closing marker. A private key between `-----BEGIN ... PRIVATE KEY-----` and `-----END ... PRIVATE KEY-----` loses its body and keeps its markers, indentation and quotes, also when the window starts or ends inside the key, and a line holding nothing but a base64 run of 40 or more characters is redacted as a key body too. Each window is scrubbed together with up to 50 lines above it, which are then dropped, so a key, heredoc opener or sensitive call that opens above the window's first line still has its value redacted inside the window; one opened further up is not caught. Lines are scrubbed before they are capped, as before. Nothing to do on upgrade

## [1.0.9] - 2026-10-05

### Changed
- **Breaking: the buffer no longer expires, and `batch.buffer_ttl` is gone.** `FileBuffer` discarded a whole type's spool once its file had gone `batch.buffer_ttl` seconds (3600 by default) without a write, with only an info line in the internal log. So a quiet host whose cron had stopped lost everything it had captured, and the stalled drain that `oldestTimestamp()` exists to reveal disappeared with it. The API stores each item's own time and accepts an old one, so a backlog is still worth delivering. A spool is now kept until it is delivered, and `batch.max_buffer_size` is its only bound: past it the oldest items are dropped, with a logged overflow. It takes envelopes as `take()` handed them out, puts them back at the head in the order given and unchanged, keeps the newest items when that overflows `batch.max_buffer_size`, and logs a failure itself, because the caller has nowhere else to keep the items. ### Fixed
- **A batch that could not be delivered keeps its ids and capture times, and goes back to the front of the buffer.** The worker put a failed batch, the items the server reported as unprocessed and the items deferred to keep a request under the byte budget back through `addItems()`, which gave each a new id and the current time and appended it. So a batch failing for hours looked freshly captured to `FileBuffer::oldestTimestamp()`, which is how a stalled drain is told apart from one waiting for its next run, and it was sent after everything captured since. They now go back at the head of the buffer, unchanged, and a failed batch lands ahead of the items deferred from it, where it was before. Nothing to do on upgrade
- **Items the worker cannot put back are logged as lost.** When putting a batch back failed, because the buffer lock stayed contended for `batch.lock_wait`, the buffer directory was not writable or the write failed, the items were gone and only a generic lock warning said so, which read like a capture that had been skipped. Each such loss now writes `Could not return items to the buffer, items lost` to the internal log at error level, with the type and the number of items

## [1.0.0] - 2026-08-20

### Added
- **This package is now the one home of the four wire payload shapes, the endpoint table and the response matrix.** `ranetrace/ranetrace-laravel` builds its error, log, event and JavaScript-error items here instead of keeping a second description of the same field sets, addresses its batches from the same table, and reads the same per-status decisions. Two descriptions of a strictly-matched field set eventually disagree, and the disagreement surfaces as a backend 422 that discards a whole batch rather than as a failing test in either repo
- `Http\Endpoint` and `Http\EndpointTable`: where each capture type's batch goes, which key the body wraps it under, which feature name attributes it, and which config key holds its timeout. `EndpointTable::contract()` is the four types `contract/endpoints.json` names, and `with()` lets a host append one of its own (the Laravel SDK adds its analytics `page_visits`, which is not part of the shared contract). The SDK name is deliberately NOT in the table: it is per SDK, not per endpoint, so `Endpoint::userAgent('PHP')` and `Endpoint::userAgent('Laravel')` build `Ranetrace-PHP/Errors/1.0` and `Ranetrace-Laravel/Errors/1.0` from one shared feature name
- `Http\ResponsePolicy`, `Http\BatchOutcome`, `Http\BatchCounters` and `Http\PauseScope`: the response matrix as data. One authority answers, per status, whether the batch goes back on the spool, what pauses and for how long, whether the items are terminal, and what the 200 counters and `unprocessed_indexes` mean. `Worker\Worker` consumes it, and so does the Laravel SDK's queued batch job. `BatchOutcome::$transient` is the seam between their two shapes: this package has no queue to release to, so a transient failure pauses on the spot and the next run is the retry, while the Laravel job spends its 60/300/900s envelope first. Both land on the same pause, which is the half the contract fixes
- `Errors\ErrorContext`: everything about the host an error item needs and a throwable does not carry. `fromServer()` derives it from a `$_SERVER`-shaped array, which is all a plain PHP host has; `provided()` takes each value as stated, which is what a framework adapter has. The values are RAW, so truncation, masking and redaction stay in one place and the two SDKs cannot bound the same field differently
- `Errors\PayloadBuilder` redacts the secret-bearing path segments of the reported URL and of the `Referer`, when the host can name them. A path segment carries no marker saying it holds a token and this package has no router to ask, so the values stay the caller's to supply: `ErrorContext::provided()` takes the current request's, plus a resolver for the `Referer`, which describes a request that is NOT the one being reported and so has to be matched separately. A host that cannot say keeps the previous query-only behaviour
- `Logging\LogItemBuilder`, `Events\EventItemBuilder` and `JavaScript\ErrorItemBuilder`: the three remaining item shapes, lifted out of the handler, the tracker and the relay so both SDKs compose the same keys, caps and markers. The event and JavaScript-error fingerprints arrive already hashed rather than being computed there: the builder is handed a finished observation of a request, not the request itself. `Support\FingerprintGenerator` is where both SDKs derive them
- `Support\Scrubber` and `Support\Diagnostics`, the two collaborator interfaces the shared builders take, so the builders depend on the capability rather than on a class. `SecretScrubber` and `InternalLogger` implement them, so nothing changes for this package; the Laravel SDK keeps its own `Diagnostics`, which writes to its dedicated log channel rather than to a file under the buffer directory
- `JavaScript\CaptureScript::withConfig()`, the seam that makes this package the one home of the browser capture script. It returns the bare script body with a caller-supplied runtime config substituted into it, and deliberately no `<script>` tag: the tag's attributes are the host's business, since this SDK takes a nonce as an option while the Laravel SDK asks `Vite::cspNonce()` for one. `ranetrace/ranetrace-laravel` carried a byte-identical copy of the same ~370 lines inline in `error-tracker.blade.php`, and because each SDK's relay validates exactly what its own copy sent, a fix applied to one silently stranded the other: nothing failed until a browser posted a shape the other relay did not accept. Both SDKs now render `resources/js/error-tracker.js`, each supplying its own config
- The capture script can send an `X-CSRF-TOKEN` header, when and only when the host puts a `csrfToken` in the config. The Laravel SDK's relay sits behind CSRF middleware and needs it; this SDK's relay verifies `Origin`/`Referer` instead and supplies no token, so nothing about what this SDK's script sends has changed. A capability only one host has now lives behind config rather than in a forked script, which is the rule for anything the two hosts do differently. A blank token counts as no token: it means no session was started, and an empty header would fail the check anyway
- Every captured item is held to a per-item byte budget on its way to the buffer: 70 KB JSON-encoded per item, 8 KB per field. Ported from `ranetrace/ranetrace-laravel` (`BaseRanetraceJob::capItemBytes()`) and already recorded as `client_item_policy` in `contract/envelope.json`, which the contract suite now asserts the constants against. An item within the budget is untouched. Over it, every string field above the per-field budget is cut and suffixed `... (truncated)`, and every array field above it is replaced wholesale, because truncating a structure mid-way yields invalid JSON. The capture paths already cap their own fields, but they cap characters where the API weighs bytes, and they cap fields one at a time where the budget is per item: twenty breadcrumbs of 5 KB each is 100 KB with no single cap exceeded. Without the budget one such item sits in the buffer until the worker sends it, and because the batch trimmer always keeps at least one item (a single item cannot be split) it draws a 413 that discards the whole batch and pauses the feature for fifteen minutes
- An item still over budget after shrinking is dropped outright and the loss is written to the internal log, under a message distinct from the shrink one. It is deliberately NOT replaced with a marker payload: the wire shape is an allow-list per type, so a top-level marker key belongs to no type, and on the errors endpoint strict field matching would reject the item and take the whole batch of up to a thousand items with it, which is the exact failure the budget exists to prevent. Losing one item is cheaper. The nested `_truncated` marker inside a free-shape field (log `context` and `extra`, JavaScript-error `context`, breadcrumb `data`) is a different thing and is unchanged
- The policy lives in one class, `Support\ItemByteBudget`, applied at each of the four buffer handoffs (errors, events, logs, JavaScript relay). This SDK has no base job to hook the way the Laravel SDK does, and the buffer implementations stay generic on purpose, so the four call sites share the class rather than each repeating the policy or it being buried in `FileBuffer`. It runs after scrubbing, so cutting a string cannot expose a secret past a redaction
- **This package is now the one home of `SecretScrubber`, `PayloadSizer` and `FingerprintGenerator` as well.** `ranetrace/ranetrace-laravel` deleted its copies of all three, along with the `CoreScrubber` bridge that stood in for the merge. Redaction and fingerprint derivation are promises to the same backend from two SDKs, and the copies had already drifted: nine test cases apart in the scrubber suites, and a fingerprint salt that fell back to `APP_KEY` on one side and to the API key on the other
- `SecretScrubber::scrubDeep()` and `scrubUrlPath()` take a CALLABLE for `$sensitiveValues`, alongside the fixed list and null they already took. A callable is asked, per URL-shaped value, which of that URL's path segments hold a secret. This is what the Laravel SDK needed and a single pre-resolved list could not give it: free-form data (breadcrumbs, log context, event properties) carries URLs from requests other than the one being handled, and one shared list would redact the wrong URL's secret. ### Fixed
- `SecretScrubber::scrubString()` no longer backtracks super-linearly, so the PCRE give-up it used to provoke is now practically unreachable. The pattern's leading `[\w.\-]*` re-tried every prefix length at every start position, which on a long run of word characters (a stack trace, a base64 blob in a log message) is quadratic: a 50k run cost billions of steps and ended at the backtrack limit, where the whole value was redacted wholesale. Three changes make it linear. A `(?<![\w.\-])` guard means a match can only start where a key token can, so a long run is entered once instead of once per character; the prefix is bounded to 64 characters, which is far more than any real key name has before its sensitive fragment; and the suffix is possessive, since the separator characters it would give word characters back for are all outside the class, so that backtracking never helped. A 50k adversarial input now completes in well under a millisecond and gets the precise redaction instead of losing the whole string. Fail-closed behaviour is unchanged and still covered: PCRE can still give up on bad UTF-8 or a host-lowered `pcre.backtrack_limit`, and the value still becomes `[REDACTED]` with a line in the internal log. The one case the new spelling gives up on deliberately is a sensitive fragment buried more than 64 characters into a single unbroken token

### Security
- URL values inside breadcrumbs, log context and event properties are now recognised by their **shape** rather than by an `http(s)://` prefix. Previously a relative URL passed through untouched, so a signed download link recorded as `/exports/42/download?expires=…&signature=…` shipped its signature while the identical absolute URL was redacted. The shape test is deliberately strict (no whitespace, none of the characters that only turn up in prose, JSON and code, and a query that is a run of `key=value` pairs) because the redaction rewrites the query, and the fragment when that is query-shaped too, and a looser test would truncate a JSON log-context payload mid-structure. A value that fails the test is left byte-for-byte alone
- `SecretScrubber::scrubDeep()` takes the host's declared sensitive path segments and redacts them inside URL-shaped values, so a reset link the tracker recorded as a navigation breadcrumb loses its `{token}` the same way the top-level `url` field already did. Without it the same payload redacted the secret in one field and shipped it in another. A path segment carries no marker saying it holds a token and this SDK has no router to ask, so the values stay the caller's to supply: `Relay` and `EventTracker` pass whatever was given to their `setSensitivePathValues()`, and passing nothing keeps the previous query-only behaviour. This SDK's Monolog handler names none, so its log context stays query-only; a host that can name them passes them to `LogItemBuilder::build()`
- The JavaScript error `message` is scrubbed the way the sibling `stack` field already was. The bundled snippet's `unhandledrejection` handler `JSON.stringify`s the rejection value into `message`, so a rejected API response carrying an `api_key` reached the backend in full while the same text inside `stack` was redacted
- The JavaScript error relay's `timestamp` and `breadcrumbs.*.timestamp` fields are capped at 64 characters. They had no length rule and nothing downstream bounded them, so an unauthenticated client could buffer an item limited only by `post_max_size`, large enough to draw a 413 that discards the whole batch and pauses JavaScript error capture

- `SecretScrubber::scrubString()` now fails closed. Its pattern backtracks super-linearly on a long run of word characters, so PCRE can hit its backtrack limit and give up; the method then returned the input, shipping the exact string it had been asked to redact. It now returns `[REDACTED]` for the whole value and writes `preg_last_error_msg()` to the internal log, so a scrubber that has started swallowing strings is visible rather than silent. Losing the string beats leaking it
- The URL fragment is scrubbed. `scrubUrl()` copied it through untouched and `scrubUrlPath()` stopped at the first `?` or `#`, so both shapes of fragment secret survived: the query-shaped `/callback#access_token=…&expires_in=…` an OAuth implicit-flow redirect comes back as, and the path-shaped SPA hash route `/app#/reset/{token}`. A fragment that is query-shaped, judged by the same strict `key=value` run the relative-URL shape test uses, now goes through query scrubbing, and any fragment goes through path-segment scrubbing, which only replaces a segment that exactly equals a declared sensitive value. A fragment of any other shape, an anchor such as `#section-2`, comes back byte-for-byte
- `scrubUrlPath()` recognises a URL's scheme only at the start of the string. It searched for `://` anywhere, so a relative URL carrying an unencoded absolute one in its query or fragment (`/reset-password/{token}?next=https://app.test/dashboard`) put the path window inside the query, inspected the wrong substring as the path, and shipped the live token. The anchored match also covers the protocol-relative `//host/path` form, which used to be read as a path and is now read as an authority
